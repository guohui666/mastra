学习指南

Mastra 框架学习指南

Mastra 是 TypeScript 框架。它用来做 AI agent 和 AI 应用。你在服务端注册 Agent、Tool、Workflow，再用 HTTP、React 或现有 Web 框架接到前端。它也能作为独立 server 部署。

  • 核心包@mastra/core 1.85.0
  • 许可Apache-2.0，ee/ 另计
  • 本地 Studiolocalhost:4111

抽查对象是当前仓库工作副本。包版本会变。第 1–10 节逐句出处是 explorations/mastra-framework-learning-guide.md，只转写对上源码或文档的内容。第 11 节是 2026-11-19 按 upstream 10b2d3fc6d 直接对照各包 CHANGELOG 和文档新增的梳理。

03 心智模型

这些对象都挂到一个 Mastra 实例上。Mastra 是注册表和协调器。类在 packages/core/src/mastra/index.ts。

概念解决什么怎么接
Agent目标不固定。模型自己决定调哪些 tool、循环几次、何时停。new Agent({...})，放进 new Mastra({ agents })。
Tool模型可调用的函数。用 schema 描述输入输出。挂到 Agent 的 tools，或单独注册到 Mastra.tools。
Workflow步骤和顺序事先写好。默认用内置引擎。createWorkflow 后 .then() / .branch() / .parallel()，再 .commit()。
Memory让后续请求看到以前的消息和抽取后的事实。@mastra/memory 的 Memory 挂到 Agent。调用时传 thread 和 resource。
Storage进程退出后仍保存 memory、workflow snapshot、trace、score、schedule 等。new Mastra({ storage })。类型是 MastraCompositeStore。
RequestContext单次请求的值。例如用户等级、locale。它不是跨请求的记忆。new RequestContext()，传给 generate、stream、workflow 或 tool。Tool 的 execute 第二个参数里总有 requestContext。
Processor在模型调用前改输入，或在返回用户前改输出。也可以处理 API 错误。挂到 Agent 的 inputProcessors、outputProcessors、errorProcessors。接口 Processor 至少有 id。
Scorer / Eval给不确定的模型输出打数字分。createScorer 在 @mastra/core/evals。预置 scorer 在 @mastra/evals。
Observability记录 agent run、workflow step、tool call、model 调用的 span，并带出 log、metric、feedback。new Mastra({ observability })。实现来自 @mastra/observability。

一条请求怎么走

  1. HTTP 进入 server。middleware 可以写入 RequestContext。
  2. Server 找到已注册的 Agent 或 Workflow。
  3. Agent 先跑 inputProcessors，再按 instructions 和 model 调用模型。
  4. 模型要外部数据时调用 Tool。inputSchema 先校验。execute 再做运行时检查。
  5. 若 Agent 配了 Memory，这次调用要带 thread 和 resource。消息写入 Storage。
  6. outputProcessors 处理模型结果。
  7. 若配了 observability，这次 run 成为一条 trace。
  8. 若步骤必须固定，用 Workflow。suspend() 把 snapshot 写入 Storage，之后 resume()。

Agent 和 Workflow 可以互相调用。Agent 的 workflows 字段能挂 workflow。Workflow 可以用 createStep 包住 agent 或 tool。源码导出 createStepFromAgent、createStepFromTool。文档入口是 docs/src/content/en/docs/workflows/agents-and-tools.mdx。

Agent

类型 AgentConfig 在 packages/core/src/agent/types.ts。类 Agent 在 packages/core/src/agent/agent.ts。导入路径文档用的是 @mastra/core/agent。

必填：id、name、instructions、model。当 editor 把 instructions 交给 Studio 时，代码里不能再写 instructions。

  • instructions：字符串、消息，或按 requestContext 动态返回。
  • model：provider/model 字符串、配置对象、fallback 数组，或函数。
  • tools：静态或动态。
  • memory：DynamicArgument<MastraMemory>。
  • inputProcessors、outputProcessors、errorProcessors、maxProcessorRetries、errorProcessorDefaults。
  • 另外还有 agents（subagent）、workflows、scorers、skills、voice、channels、browser、workspace、hooks、durable、signals、goal、requestContextSchema。

调用：.generate() 返回完整结果。.stream() 按 token 流式返回。

Tool

工厂是 createTool，从 @mastra/core/tools 导入。ToolAction 把约束和执行分开：

  • 形状放 schema：inputSchema、outputSchema、suspendSchema、resumeSchema、requestContextSchema。
  • 动作放 execute。签名是 (inputData, context) => Promise<...>。第一个参数是已经按 inputSchema 校验的输入。第二个参数里的 requestContext 总是有。
  • 审批放 requireApproval。暂停前的检查可放 beforeApproval。
  • outputValidation：'strict' 或 'warn'。

这和仓库规则一致。规则在根目录 AGENTS.md：确定性的形状、类型、范围、格式、字段间约束放 schema，不要放进 execute。授权、是否存在、冲突、外部 API 结果留在 execute。规则是写法约定，不是类型系统强制。文档里的 execute 可以只写第一个参数。

07 一条最小用法

下面每步都能对上文档。代码只保留文档里的必要片段。

  1. 创建项目：npm create mastra@latest。
  2. 若要手写最小 Agent，按 docs/src/content/en/docs/getting-started/_partial-agent-quickstart.mdx 安装依赖。
  3. 写 Tool。文档是 agents/tools.mdx。形状是 createTool({ id, description, inputSchema, outputSchema, execute })。execute 的第一个参数是校验后的输入。
  4. 写 Agent。文档是 agents/overview.mdx。
  1. 本进程直接调：mastra.getAgentById('test-agent')，再 agent.generate(...)。
  2. 要给前端调：先 npx mastra dev。再在另一个应用里 new MastraClient({ baseUrl: 'http://localhost:4111' })，client.getAgent('test-agent').generate(...)。注册表 key 和 agent id 在文档示例里经常相同。若不相同，服务端 getAgent 用的是 Mastra 配置对象的 key。Client 的 getAgent 参数名是 agentId。本次没有逐条核对 HTTP 路径用 key 还是 id。接前端时先看 http://localhost:4111/api 或 Swagger。
  3. React：用 MastraReactProvider 包住应用。子树里用 useMastraClient() 或 useChat()。
  4. 若聊天 UI 已经是 Vercel AI SDK：在 Mastra 的 server.apiRoutes 加 chatRoute({ path: '/chat/:agentId' })。前端 useChat() 打这个 path。

要记忆时再加 @mastra/memory 和 @mastra/libsql。不要在没有 storage 的情况下假设消息会留下。

意图识别

没有名为「意图识别」的单独产品。对应能力是 Classifier。

Classifier 向决策模型提固定问题，返回带类型的答案。它不解析模型生成的自由文本。问题有三种：

  • choice：在你写的类别里选一个，例如 billing、support。
  • score：打一个数字分。
  • boolean：给出「是」的概率。

Workflow 里用 .classifier(router)，再 .branch() 按答案走不同步骤。也可以挂到 Agent 上。ClassifierProcessor 根据答案调用 abort() 或 filter()。

类别不固定、步骤也不能事先写死时，用 Supervisor。主 Agent 看子 Agent 的 description，自己决定交给谁。

依据：docs/src/content/en/reference/classifier/classifier.mdx；docs/src/content/en/docs/workflows/control-flow.mdx；docs/src/content/en/reference/processors/classifier-processor.mdx。

决策模型

厂商已经提供 decisionModel() 时，接入很短。Classifier 只接受决策模型。它不接受 'provider/model' 字符串，也不接受普通语言模型。

文档写明 OpenAI、Anthropic、Google、TypeSafe AI 都有 decisionModel()。旧名字 evaluationModel() 还在，是废弃别名。Mastra 调用 doDecide()。旧 provider 只有 doEvaluate() 时，会走这个旧方法。

同一份 Classifier 可以放进 Workflow、ClassifierProcessor，或 Tool 审批。模型拒绝回答时，答案类型是 refusal。choice 是 undefined。

自建模型要实现 AI SDK 的 DecisionModelV4。核心方法是 doDecide()。MastraDecisionModel 包住它。没有这个接口的聊天模型，不能直接放进 Classifier。那种情况用普通 Agent 做 Supervisor。

依据：docs/src/content/en/reference/classifier/classifier.mdx；packages/core/src/classifier/index.ts；docs/src/content/en/docs/agents/human-in-the-loop.mdx。

  • Studio：npm run dev 或 npx mastra dev。地址是 http://localhost:4111。可以聊天、换模型、看 tool call 和 trace、逐步跑 Workflow、测 tool。
  • 本地数据：LibSQLStore，url: 'file:./mastra.db'。不配 storage 时，数据在内存里，进程退出就没了。这个文件适合单进程本地使用。

类似 Zcode 的本地应用

可以做 Agent 运行时。Mastra 不自带 Zcode 那种桌面端。

Zcode 是智谱的本地 Agentic Development Environment。它打开一个项目目录。Agent 在同一个任务里改文件、跑终端、看 Git、预览页面，并一直做到目标完成。桌面窗口、编辑器和审查界面是产品本身。

  • 本地工作区：LocalSandbox 的 workingDirectory。execute_command 可以跑 Git、构建和测试。
  • 长任务：Agent 的 goal。目标存在 thread 里。judge 模型判断是否完成，或预算用完才停。需要 storage 和 Memory。
  • 本机数据：file:./mastra.db。
  • 扩展：MCP、Skills、Browser。
  • 界面：本机 server 起来后，用 @mastra/client-js 接 Electron 或 Tauri。Vue 页面也能接。

要自己做的是产品壳：窗口、文件树、编辑器、diff 审查、终端面板、权限弹窗。Studio 是开发调试界面，不是这个桌面 IDE。

审批危险操作

支持。Tool 执行前可以停下来等人批。模型已经选好工具和参数，execute 还没跑。

  • 某个 Tool 上设 requireApproval: true。只拦这个工具。
  • 某次 stream() 或 generate() 上设 requireToolApproval: true。这次调用里的每个工具都要批。
  • requireToolApproval 也可以是函数。它能看到 toolName、args、requestContext。返回 true 才暂停。文档示例用 Classifier 判断这次调用是不是破坏性、不可逆、很贵，或碰到敏感数据。函数抛错时，默认改成要审批。

流里会出现 tool-call-approval，里面有 toolCallId、toolName、args。你调用 approveToolCall() 或 declineToolCall()。拒绝时可以带 reason。模型会看到这句话。不写 reason 时，模型收到 Tool call was not approved by the user。

Workspace 工具另有一层。tools.requireApproval 默认是 false。可以只给写文件、删文件、跑命令打开。requireReadBeforeWrite: true 时，Agent 必须先读过这个文件，才能改它。

文件工具和命令工具的策略是分开的。你只拦写文件，Agent 仍可能用 execute_command 去写同一个路径。LocalSandbox 默认就在本机跑命令。文档写明它不是隔离的，也不算安全。

源码层还有两个配置位（packages/core/src/tools/tool.ts:273）。needsApprovalFn 是每个工具自己的权威判定，存在时优先于 requireApproval，运行时按参数动态决定。beforeApproval 在审批门之前跑，返回 { proceed: false, output } 可以不挂起、直接把 output 还给模型。明显不合法的调用在这里挡掉，不打扰人。

等人不是阻塞线程。run 会 suspend()，快照落到 workflows 存储；流里推 tool-call-approval chunk，payload 带 runId、toolCallId、toolName、args、resumeSchema（loop/workflows/agentic-execution/tool-call-step.ts:577）。所以审批可以发生在几分钟后、另一个进程、甚至服务器重启之后。HTTP 侧四个入口：POST /api/agents/:id/approve-tool-call、/decline-tool-call、GET /suspended-runs（重启后仍可找回）、POST /resume-stream（带 runId + resumeData 续流）。

这一节只覆盖执行前审批。执行中的 suspend()、Workflow 的暂停和恢复、拒绝用的 bail()，见下方三节。把审批接到飞书等外部平台，见「审批接外部平台」。

Suspend and resume

这是 Workflow 的暂停引擎。一个 step 的 execute 里调用 suspend()，整条 workflow 停在这一步。当前状态写成 snapshot，存进你配的 storage。进程重启、换一次部署之后，还能用同一个 runId 接着跑。

这一步可以声明两份 schema。

Schema谁来填做什么
suspendSchemastep 调用 suspend(payload)告诉外面为什么停、还缺什么
resumeSchema之后的 resume({ resumeData })把人、回调或定时器交来的数据送回 step

execute 能拿到 inputData、resumeData、suspend、suspendData。第一次进入时 resumeData 是空的。条件不满足就停。

run.start() 回来时看 status。停住时它是 suspended。result.suspended 是停住的路径。嵌套 workflow 时，一项可以是 ['nested-workflow', 'step-1']。result.steps[stepId].suspendPayload 就是传给 suspend() 的内容。

调用 await suspend() 时，引擎做这几件事：

  1. 停在这一步。
  2. 把 workflow 当前状态写成 snapshot。
  3. 把 snapshot 写入 storage。
  4. 把这一步标成 suspended。
  5. 以后 resume() 读回这份 snapshot，从这一步再往下走。

Snapshot 里有：每个 step 的状态、已经完成的 step 的输出、走过的路径、暂停中的 step 和它的 metadata、每个 step 还剩的重试次数、恢复所需的上下文。示例 JSON 里能看到 runId、status、context.input、某一步的 suspendPayload、resumePayload、serializedStepGraph、suspendedPaths。

已经成功的 step 留在 snapshot 里，恢复时不再跑。停住的那个 step 会再进一次 execute。这次带上新的 resumeData，以及上次 suspend() 存下的 suspendData。

resume() 可以从 HTTP、按钮、定时器或别的进程调用。只有 runId 时，先用这个 id 建回 run。

参数作用
resumeData符合这一步 resumeSchema 的数据。可选。
stepstep 对象、step id，或它们的数组。传对象时 resumeData 有类型。只停了一个 step 时可以不传。停了多个时必须写明。
requestContext这次恢复使用的 request context。
forEachIndex.foreach() 里从 0 开始的某一轮。其它轮继续停着。不传时，这一 step 里所有停住的轮次都用同一份 resumeData。
retryCount嵌套 workflow 的可选重试次数。
outputOptions.includeState为真时，结果里带上 workflow state。
tracingOptions根 span 名字、metadata、tags、trace id。开了 tracing 时，结果上还有可选的 traceId 和 spanId。

result.suspended[0] 可以直接传给 step。进程不在了，用 workflow.getWorkflowRunById(runId) 把 snapshot 读回来，再用 createWorkflowStateReader() 看停在哪一步。嵌套 workflow 用 suspendedStep.path。resume label 指向 foreach 的某一轮时，上面有 foreachIndex。

同一时刻只有一个 resume() 能继续这次暂停。它先把存下来的状态从 suspended 改成 running。另一个调用会抛 WORKFLOW_RESUME_ALREADY_CLAIMED，step 不会再跑。HTTP 上后到的那次返回 409 Conflict。支持原子更新的 storage 才会强制执行。文档点名做不到的有 ClickHouse、Cloudflare D1、Cloudflare KV、Cloudflare Durable Objects、LanceDB、Redis。shouldPersistSnapshot 把 running 排除掉时，这次认领也会跳过。

.sleep(毫秒) 和 .sleepUntil(日期) 停在 workflow 这一层，状态是 waiting。suspend() 停在某一个 step 里面，状态是 suspended。Run 参考页还把 waiting 写成：执行在结束前被打断，例如 executor 被 abort。两页都写了 waiting，触发原因不完全相同。

Workflow 人审

人审是 suspend 的一种用法。停下来是为了等人批、拒，或补数据。suspend({ reason }) 把原因交给界面。人提交后调用 resume({ resumeData })。

人明确拒绝时用 bail()。bail() 后面的逻辑不跑。它不抛错。文档写 workflow 以 success 结束，结果是传给 bail() 的 payload。

Run 参考页把 bailed 写成：某一步调用了 bail()，run 本身以 success 结束。默认引擎在返回前把内部的 bailed 改成 success（packages/core/src/workflows/default.ts）。step 处理函数里先记的是 status: 'bailed'（packages/core/src/workflows/handlers/step.ts）。类型 WorkflowRunStatus 里仍有 bailed。

第一次进入时 approved 是空的，!approved 为真，所以会暂停。人传 approved: false 时，这个条件仍然为真，还会再暂停。拒绝要单独写成 approved === false，然后 bail()。文档里的顺序是：先处理 false 并 bail()，再处理「还没有答复」并 suspend()，最后才做真正的动作。

多步审批时，每一步有自己的 resumeSchema 和 suspendSchema。每一步要单独 resume() 一次，按顺序来。

Agent 人审

Agent 停的是一次 tool call。文档写了两种机制。都要用 snapshot。Mastra 上要配 storage，否则会看到 snapshot not found。Agent 的 snapshot 只留恢复这次 run 所需的数据，run 结束后就删。对话历史看 Memory。执行记录看 tracing。

执行前审批。模型已经选好工具和参数，execute 还没跑。两个开关是「或」。任意一个为真，这次调用就停。短说明和 Workspace 那一层开关见上面的 审批。

开关放在哪拦住谁
requireApproval: truecreateTool()只拦这个工具
requireToolApproval: true这次 stream() 或 generate()这次里的每个工具

requireToolApproval 也可以是函数。它能看到 toolName、模型传入的 args、requestContext、workspace。返回 true 才暂停。函数可以是 async。文档示例用 Classifier 判断，并且只把参数名交给决策模型。函数抛错时，默认改成要审批。返回 true 只是交给人批，不会自动批准或拒绝。

运行时再把函数结果和工具自己的 requireApproval 合在一起。工具上的布尔 true 一定要批。工具上的布尔 false 关不掉调用级的 requireToolApproval。工具上的 requireApproval 如果是函数，就以这个函数为准。

Durable agent 和 stored agent 会把选项存下来。函数存不了。这两个场景只能传布尔值。传了函数，就变成每个工具都要批。

stream() 的 fullStream 里出现 tool-call-approval。chunk.payload 有 toolCallId、toolName、args。然后调用 approveToolCall({ runId, toolCallId }) 或 declineToolCall({ runId, toolCallId, reason })。

reason 会代替工具结果交给模型，也会写进这次 tool call 的 approval metadata。不写 reason 时，模型收到 Tool call was not approved by the user。declineToolCallGenerate() 和 declineNetworkToolCall() 同样可以带 reason。

generate() 不流式。工具要批时，它马上返回。finishReason 是 suspended。suspendPayload 里有 toolCallId、toolName、args。还有 runId。继续用 approveToolCallGenerate() 或 declineToolCallGenerate()。

四个方法上的 toolCallId 都可选。多个工具同时等着时要传。常见于 Supervisor。不传就恢复最近那一次。

敏感工具可以把批准绑到当时给人看的工具名和参数上。文档用 beforeToolCall hook。批准前对 toolName 和 args 做指纹。生产环境要用稳定 hash。批准时把指纹放进存储，hook 对上了才放行，并且只用一次。参数在批准后变了，旧批准不能用。生产里要把指纹按用户、run、tool call、策略版本存进持久存储。

执行中暂停。execute 已经开始，发现还缺数据或还要确认，就 return await context.agent.suspend(payload)。suspendSchema 规定你问用户什么。resumeSchema 规定用户回什么。流里是 tool-call-suspended。接着跑用 resumeStream(resumeData, { runId })。

suspend() 不抛错。await suspend(...) 后面的代码仍会先跑完，工具才真正停。所以要立刻 return。

子 Agent 跑不了没有 execute 的 client tool。工具既要一份结构化答复，又要在子 Agent 里跑时，用 suspend()。暂停会传到 Supervisor。

一次暂停或审批被清掉后，流里会有 tool-call-resumed，toolCallId 与原来相同。它出现在这次的 tool-result 之前。payload.kind 是 suspension 或 approval。只有真的清掉一次暂停或审批时才发出。@mastra/ai-sdk 里对应 data-tool-call-suspended 或 data-tool-call-approval，并带 resumed: true。用这个信号标问题已经答过。暂停来自子 Agent 时，委托调用的输出是子 Agent 的结果，不是用户刚交的答复。

下一句话自动接着跑。在 defaultOptions 或这一次请求上设 autoResumeSuspendedTools: true。用户在同一条 thread 上发下一句时，Agent 按 resumeSchema 抽出 resumeData，再恢复工具。需要 Memory、同一条 thread 和同一个 resource，以及工具上的 resumeSchema。这不批准 requireApproval。那种工具一直停着，直到明确批准、拒绝，或 resumeStream({ approved: boolean })。resumeStream() 留给 webhook 和按钮。自动恢复留给对话。

页面刷新或换机器。内存里的 runId 没了，就用 listSuspendedRuns()。它从 @mastra/core@1.43.0 开始有。查的是还停着的 agent run。

可选过滤还有 fromDate、toDate。page 从 0 开始。perPage 和 page 一起传才分页。每个 run 有 runId、status: 'suspended'、可选的 threadId 和 resourceId、suspendedAt、toolCalls。审批暂停才有 args。suspend() 暂停才有 suspendPayload。

结果只包含你调用方法的那个 Agent。Supervisor 看得到自己的外层 run。子 Agent 的内层 run 只有在子 Agent 上查才看得到。Snapshot 只在 run 还等输入时保留，run 结束后就删。@mastra/pg 和 @mastra/libsql 在数据库里按 thread 和 resource 过滤。其它 storage 先取出，再在进程里滤。HTTP 是 GET /agents/:agentId/suspended-runs。client SDK 同名方法也能查。sendToolApproval() 在 Memory 里找不到活跃 run 时，会先到 storage 里找。同一条 thread 配上多个暂停 run 时，要传 toolCallId。

默认的内存 storage 在进程退出后丢掉 snapshot。要跨重启，就配持久 storage。

Supervisor。子 Agent 的工具要 requireApproval，或在 execute 里 suspend()，请求会传到最外层。多层委托也一样。你在 Supervisor 的流上批、拒，或 resumeStream()。决定再传回子 Agent。generate() 时看 finishReason === 'suspended'，然后 approveToolCallGenerate({ runId, toolCallId })。

接 MCP

包是 @mastra/mcp 2.5.0。MCPClient 去连别人的 MCP server。MCPServer 把 Mastra 的 agent、tool、workflow、prompt、resource 暴露给别的 MCP 客户端。传输是 stdio 和 Streamable HTTP。

2.0 起，你自己的 server 只提供修订 2026-07-28。不再协商更旧的修订。每个请求自己带齐状态。initialize 握手、session header、单独的 HTTP+SSE 传输，以及 server 主动发起的请求都去掉了。Streamable HTTP 的响应仍然可以是 SSE。去掉的是独立的 GET /sse 加 POST /messages。2.0 server 上这两条路径返回 404。客户端应打 /mcp。

  • forwardInstructions 默认 false。打开后，会把 server 广告的 instructions 追加到 Agent 的 system prompt。默认最多 512 个字符。
  • onToolError 默认 'throw'。2.5.0 起，'return' 给出完整的 CallToolResult，不再只给 structuredContent。

暴露 MCP

id 必填。注册后可以用 getMCPServerById() 拿回来。参考示例里，agent 会变成工具 ask_myAgent，workflow 会变成工具 run_dataProcessingWorkflow。只在本进程里用自己的 tool 和 agent 时，不必包一层 MCP server。

每个请求自包含，长驻进程和 serverless 用同一套。自己用 Node HTTP 时调用 startHTTP({ url, httpPath, req, res, options })。options 只剩 enableDnsRebindingProtection、allowedHosts、allowedOrigins。本地命令行用 startStdio()，再把构建产物写进包的 bin。

工具、resource、prompt 要向调用方要数据时，调用 suspend()，并声明 resumeSchema。server 把这一轮变成 input_required。调用方答完后，处理函数再跑一次，答案在 resumeData 里。resumeSchema 必须是一层普通字段。调用方拒绝或取消时，这次调用以错误结束，工具不会再跑。Client 在该 server 上写 inputRequests。不写的话，input_required 会变成错误。

继续令牌是签名过的 requestState。它不是加密。被改过、过期，或属于别的工具、别的参数、别的调用方时，处理函数之前就拒绝。多台机器要能接着答，就用 requestState: { key, ttlSeconds } 共用一把 key。没有授权时，谁拿到这个字符串谁就能答，直到过期。会写数据、付钱、改账号的暂停，要放在授权后面。

server.executeTool() 和 POST /api/mcp/:serverId/tools/:toolId/execute 做完时返回 { status: 'completed', output }。等人填时返回 { status: 'suspended', suspendPayload, resumeSchema }。接着做就把同一份参数再提交一次，带上 resumeData 和回传的 suspendPayload。

Studio 还会注册一组 REST 路由，用来列 server、看 tool、执行 tool、读 resource。默认前缀是 /api。鉴权靠 server.auth。只检查 /mcp 或 /sse 的中间件盖不住这些路由。配了 Mastra FGA 时，tools/list 会过滤，tools/call 和那条 REST execute 会检查执行权限。

按用户放行

目标：用户 A 有 agent X 的权限，才放行对 X 的调用。先说限制：rules.condition(user) 只拿得到 user，拿不到路径。三个方案：

会话与存储

threadId 是一个会话，resourceId 是归属者（线程所有权隔离，FGA 校验）。每轮的处理：

  1. 客户端带 threadId 调 generate 或 stream。
  2. prepare-memory-step 组装 MessageList：系统提示 + 历史（MessageHistory 从 storage 读）+ 语义召回（SemanticRecall）+ 工作记忆（WorkingMemory）+ 新消息。
  3. 运行中 SaveQueueManager 按 step 落库：每完成一步就 memory.saveMessages，不等全部结束。
  4. onFinish 补写 response 消息，异步生成线程标题。

「多轮」的本质：每轮从存储重放历史加增量召回，模型无状态。存储链路：MastraMemory 契约 → @mastra/memory 实现 → storage 域（memory 域存 threads/messages，workflows 域存 run 快照）→ stores/* 20+ 适配器。不配 storage 时 core 有 filesystem 兜底。

Resumable streams（1.83.0）

以前只有 durable agent 发布 run 流。现在每个注册到 Mastra 的 agent 默认发布：run 的每个 chunk 发到 stream topic，并留 replay cache。效果：

  • 客户端断线重连，从缓存追上。
  • 另一个读者用 agent.observe(runId) 跟看同一次 run。
  • 任何读者能用 observe().abort() 或 agent.abortRunStream(runId) 停掉它。

Agent 字段 streams：注册的 agent 默认开，独立 agent 默认关。对象可配 pubsub、cache、shouldCache、cleanupTimeoutMs。注意它不是崩溃恢复：进程死了 run 就停。要跨重启续跑，仍用 durable agents——它们经同一层发布。文档 agents/resumable-streams.mdx。
